# Schema generation

This module deploys the schema generation Lambda and the resources it needs
to run.

The Lambda reads metadata from a PostgreSQL or Oracle database, builds an
Avro contract for each configured table and writes the contracts to S3.

The runtime code is kept separately in
`../../runtime/schema-generation/`.

## What this module creates

- A container-based Lambda
- An execution role with permissions to read the configured database secret
  and read and write contracts in the configured S3 locations
- An encrypted CloudWatch log group
- An encrypted SQS queue for failed asynchronous invocations
- CloudWatch alarms for Lambda errors, throttling and failure delivery

The database, secret, S3 bucket, encryption keys, network and ECR repository
are supplied by the environment using the module.

## Using it for different services

Each module instance is configured for one source database, one schema and
a list of tables.

The `source_config` input supplies the database engine, service name,
database name, schema name, table list and secret ARN. Oracle connections
also require either a service name or a SID.

There are no fixed service names or dependencies on the DMS modules.
An environment can create multiple instances with `for_each` when it needs
to support several sources.

Each instance needs a unique resource name.

## Database access

The database secret must contain `username`, `password` and `host`.
It can also contain `port`.

The module passes the secret ARN to the Lambda. It does not read the
credentials into Terraform.

The Lambda reads database metadata. It does not create tables or change
the source data.

The supplied subnets and security groups must allow the Lambda to reach
the database, Secrets Manager and S3.

## Contracts and versions

The caller supplies the contract namespace, service details, contacts and
contract version.

Versions use `v1`, `v2`, `v3` and so on. Uppercase versions and leading zeros
are rejected. `v0` is reserved for future migration work.

Generation does not allocate or increment versions.

Contracts are written using this structure:

```text
<source>/<database>/<schema>/<table>/<contract_version>/contract.avsc
```

Each path segment is URL-encoded by the runtime.

The Lambda checks that the generated contract is structurally valid Avro
before writing it. Compatibility checks against previous versions belong
to the separate schema validation stage.

## Existing contracts

The Lambda uses conditional S3 writes to avoid replacing an existing
contract.

If the same contract already exists, generation returns `ALREADY_EXISTS`.
If the location contains different contract content, generation fails.

When several tables are processed, contracts already written successfully
are kept if another table fails. The invocation reports the failure so
the caller can handle it.

Bucket versioning, retention and access policies are managed by the
component that owns the bucket.

## Permissions and encryption

S3 access is limited to the object ARN patterns supplied to the module.
These patterns must cover the paths generated by the runtime.

Secret access is limited to the configured secret ARN. Encryption-key
permissions are limited to the supplied key ARNs.

The owners of the keys must also provide suitable key policies.
The CloudWatch Logs key must allow the regional Logs service to use it.

The module does not grant access to DynamoDB or DMS.

## Invocation and failures

The module does not create a schedule or an event trigger. The environment
or workflow decides when generation runs.

For synchronous invocations, the caller handles function errors.

For asynchronous invocations, Lambda retries according to the configured
settings. Events that exhaust their retries or expire are sent to the
failure queue. Messages are not replayed automatically.

Registration remains a separate stage. The workflow must ensure that
contracts have passed the required validation before they reach it.

## Container image

The image must be published before deploying the Lambda.

Supply an ECR image URI pinned to a SHA-256 digest. Its architecture must
match the configured Lambda architecture.

Terraform deploys the image; it does not build or publish it.

## Operational settings

Timeout, memory, reserved concurrency, log retention and retry settings
are configurable.

Reserved concurrency should reflect both the AWS account quota and the
number of connections the source database can support.

Alarm notification destinations are optional. Without them, alarms are
created but do not send notifications.

Configuration is passed through Lambda environment variables, which have
a combined size limit of 4 KB. Large table lists may need to be split
across instances or moved to an external configuration mechanism in
future.
